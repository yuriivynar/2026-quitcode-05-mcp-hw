# Threat model: MCP-інтеграції LeadDesk (Task D)

Спирається на `.mcp.json`, `.claude/settings.json`, код `mcp/leaddesk-server/src/server.mjs` і на те, що агенти робили в сесіях Task B–C (`docs/mcp/connections.md`, `docs/mcp/verification.md`, `docs/mcp/ab/`). Підключено чотири сервери: `supabase`, `vercel`, `playwright` (третій сервер за вибором, Figma не підключали) і власний `leaddesk` (його немає в `.mcp.json`: у Task C його підключали лише скоупом `local` у теці прогону B, `docs/mcp/ab-generic-vs-domain.md:10`). Усі дані в цій роботі синтетичні, але модель описує, що було б у клієнтському проєкті.

## Які дані бачить агент

| Сервер | Що потрапляє в контекст агента | Чиї це дані | Чи є там текст, який написали треті особи |
|---|---|---|---|
| `supabase` | Результати SQL: у цій роботі рядки `public.leads` (ім'я, email, компанія, джерело, статус, бюджет, текст заявки, дата), схема таблиць, публічні ключі проєкту (група `development`), пошук у документації. У Task C агент сам прочитав схему всієї таблиці. Відповіді `execute_sql` приходять у межах `<untrusted-data-…>` із попередженням моделі, але вендор сам називає це не гарантією | кінцевих користувачів клієнта (ліди) і самого клієнта | так: поле `message` пишуть відвідувачі форми, а значення `company` і `full_name` вводять вони ж |
| `vercel` | Список команд і проєктів (в одній сесії агент сам викликав `list_teams` і `list_projects` і побачив назву команди, її ідентифікатор і перелік проєктів; у файли це не записано), метадані деплоїв, лог білду, логи рантайму, коментарі toolbar. Доступний увесь акаунт: токен має єдиний OAuth-скоуп | клієнта (проєкти, інфраструктура) і його відвідувачів, якщо вони потрапляють у логи | так: логи рантайму містять введене користувачами, коментарі toolbar пишуть рев'юери клієнта, повідомлення комітів пишуть розробники |
| `playwright` | Знімки сторінки (дерево доступності), скриншоти, повідомлення консолі, список мережевих запитів; через `browser_network_request` (не в `allow`, питає щоразу) ще й заголовки та `Cookie`. Усе, що агент вводить у форму, теж | власника сайту та його відвідувачів | так: будь-який текст на сторінці, зокрема чужому, — недовірений вхід для моделі |
| `leaddesk` | Лише `id`, `company`, `status`, `source`, `budget`, `createdAt` (проєкція в `server.mjs:25`), текст ресурсу зі статусами та `reason`. Ім'я, email і текст заявки відкидаються під час завантаження і до моделі не потрапляють | клієнта (бізнес-дані лідів) | мінімально: `company` вводить відвідувач форми; `reason` складає агент, і в Task C на запиті 5 він сам придумав формулювання (`docs/mcp/ab-generic-vs-domain.md:27`) |

У сесії з Playwright є всі три складники небезпечної комбінації: недовірений текст сторінки, вбудований `Read` Claude Code (за замовчуванням читання файлів у робочій теці не питає, а `.env.local` у ній є) і `browser_navigate` в `allow`, що виконується без запиту.

## Канали виносу в цій же сесії

| Канал | Звідки (сервер або вбудований інструмент) | Як ним можна винести дані | Закрито? Чим саме |
|---|---|---|---|
| Публічний preview-деплой через MCP | `vercel`, `deploy_to_vercel` з `target: preview` (і `create_deployment`) | Агент, збитий інструкцією з логу чи коментаря, викочує сторінку з вмістом контексту на публічну адресу | Через MCP закрито `deny` (`.claude/settings.json:8`; `:18` додано після останньої сесії з Vercel, дію не вимірювали, `docs/mcp/verification.md:48`). Не закрито: git-шлях (рядок нижче) і записуючі інструменти Vercel поза `deny` (`create_project_env`, `edit_project_env`, `add_project_domain`, `assign_alias`), які стримує лише ручне схвалення |
| Публікація через git | `Bash` (`git push`) → форк на GitHub і git-інтеграція Vercel | Агент записує дані у файл, комітить і пушить: вони потрапляють у форк і через git-інтеграцію проєкту (`docs/mcp/verification.md:45`) у preview-деплой | Не закрито файлами: правил на `Bash` немає. Стримують лише запит на схвалення `Bash` і правило `AGENTS.md` про `git push`. Чи увімкнено Deployment Protection для preview, не перевіряли |
| Навігація браузера | `playwright`, `browser_navigate` | Дані в параметрах URL (`https://чужа-адреса/?q=…`) або введення в чужу форму через `browser_type` і `browser_fill_form` | Частково: `--allowed-origins http://localhost:3000` (`.mcp.json:14`) обмежує запити браузера цим origin, але вендор прямо пише, що це не межа безпеки й на редиректи він не діє; обхід не перевіряли. Самі інструменти в `allow` (`.claude/settings.json:33`, `:37`, `:38`) виконуються без запиту |
| Вбудовані інструменти Claude Code | `WebFetch`, `WebSearch`, `Bash` | Запит із даними на довільну адресу, `curl` у шелі | У проєктних файлах не закрито: ні `deny`, ні `allow` на них немає. Захист лише в тому, що у стандартному режимі Claude Code питає про кожен виклик; у прогонах Task C агент їх не запитував |
| Конектори акаунта claude.ai | Gmail, Claude Docs, draw.io (станом на 2026-10-04 `Connected`), а також Airtable, Make, n8n, Zite, claude.ai Supabase і claude.ai Vercel (потребували автентифікації). Вони прив'язані до мого акаунта й видимі в кожній теці | Набір інструментів конекторів не перевіряли. За призначенням Gmail дає доступ до пошти, Claude Docs створює документи, Make і n8n після автентифікації запускають сценарії; claude.ai Supabase, імовірно, підключено без `project_ref` на весь акаунт | Закрито лише дисципліною: у кожній сесії я вимикав їх у `/mcp` для теки. Файлом це не зафіксовано, тож не перевіряється, і нова тека без вимикання знову їх покаже |
| SQL до бази | `supabase`, `execute_sql` | Не прямий канал: у `features` немає `functions` (`.mcp.json:5`), але SQL міг би звернутися до розширення з мережею (наприклад `pg_net`), якщо воно увімкнене | Не закрито технічно: `execute_sql` лишається і без `read_only`, і з ним (прогін A у Task C, помилка `25006`). Стримує лише ручне схвалення: інструмента немає в `allow` (`.claude/settings.json:26-43`). Чи увімкнено `pg_net`, не перевіряли (це показав би `list_extensions`) |
| Власний сервер | `leaddesk` | Прямого мережевого каналу немає: у `server.mjs` немає `fetch` і запитів, лише читання локальної фікстури (`:12`, `:28`); `reason` потрапляє лише в пам'ять процесу | Закрито конструкцією, а не налаштуванням. Не закрито: якщо колись додати режим через HTTP до застосунку, канал з'явиться |

## Що ми забороняємо і чим саме

| Що заборонено | Механізм: deny, URL, прапорець, окремий акаунт, окрема сесія | Де це видно: файл і рядок | Чого цей механізм НЕ закриває |
|---|---|---|---|
| Покупки, деплой, посилання в обхід захисту, листування toolbar у Vercel | `deny` на 11 точних імен, глоб `buy_*`, точні `create_project`, `delete_project`, `create_deployment`, `cancel_deployment` | `.claude/settings.json:4-19` | Це захист на боці клієнта, токен Vercel однаково має увесь акаунт (єдиний скоуп). Кілька десятків інших записуючих інструментів (`create_project_env`, `edit_project_env`, `add_project_domain`, `assign_alias`…) лишаються без `deny`; правила `:15-19` додано після останньої сесії з Vercel, їхню дію не вимірювали. Інструмента `use_vercel_cli` у сесії Task B з Vercel не було, CLI на машині не встановлено (`docs/mcp/connections.md:5`). Але жодне правило в репозиторії не закриває шлях `Bash` → локальний `vercel`: якщо CLI колись установлять і залогінять, `deny` на `mcp__vercel__*` його не зупинить |
| Виконання довільного коду й файлів у браузері | `deny` на `browser_run_code_unsafe`, `webmcp_*`, `browser_file_upload`, `browser_drop`, `browser_evaluate`; прапорці `--isolated` і `--no-webmcp` | `.claude/settings.json:20-24`, `.mcp.json:14` | Знімок сторінки лишається недовіреним текстом, а `browser_navigate`, `browser_type`, `browser_fill_form` дозволені без запиту. Вбудований `Read` Claude Code читає будь-який файл проєкту. `--allowed-origins` не межа безпеки |
| Доступ до інших проєктів і до керування акаунтом Supabase | Один проєкт у URL: `project_ref=`, `features=database,development,docs` без `account`, `functions`, `branching` | `.mcp.json:5` | `read_only=true` свідомо не ставили, бо міграція потребує запису; у Task C прогін A із `read_only=true` не дав змінити дані (`25006 cannot execute UPDATE in a read-only transaction`), але `execute_sql` і читання лишаються. Екран згоди OAuth показує всі організації акаунта (за walkthrough), тож без окремого акаунта звуження в URL не рятує. Роль, під якою працює `execute_sql`, не перевіряли |
| Автоматичне схвалення небезпечних викликів | У `allow` лише точні імена, без `*`, без `execute_sql` і `apply_migration`; кожен такий виклик схвалюю вручну | `.claude/settings.json:26-43` | Сам `allow` без запиту схвалює три інструменти, якими можна винести дані: `browser_navigate`, `browser_type`, `browser_fill_form` (`:33`, `:37`, `:38`). Решта тримається на увазі людини: рамка схвалення для SQL (`UPDATE … WHERE … RETURNING`) читається гірше, ніж для доменного дієслова. «Always allow» записало б правило в `.claude/settings.local.json` (він у `.gitignore`, не комітиться); зараз правил `allow` там немає |
| Доступ агента до більшого, ніж два дієслова LeadDesk | Власний сервер: два інструменти замість SQL, статус лише з переліку (`z.enum`), шість полів у відповіді, запис в аудит на кожну зміну | `mcp/leaddesk-server/src/server.mjs:25` (шість полів), `:77-79` (`z.enum` нового статусу), `:80-87` (`reason` 3–500), `:93` і `:116` (рівно два інструменти), `:139-140` (запис аудиту) | `reason` — вільний текст (у `.describe` просимо без персональних даних, але це прохання, а не перевірка). Зміна статусу живе лише в пам'яті процесу й зникає після перезапуску (`server.mjs:7-8`); у режимі з застосунком вона була б постійною |
| Клієнтські акаунти та організації в агента | Окремі особисті або одноразові акаунти (Supabase з порожнім проєктом, Vercel з одним навчальним проєктом); для кожного кроку нова сесія з одним сервером, браузер ніколи разом із Supabase | `docs/mcp/connections.md:3` (акаунти), `:24-32` (сесії) | Нічого не заважає під'єднатися з іншого акаунта: це процес, а не технічна перевірка. Конектори claude.ai з'являються в кожній теці, їх вимикають вручну в `/mcp`. Інтеграцію `ide` (`getDiagnostics`, `executeCode`) у `/mcp` не видно, вона зникає лише при запуску поза VS Code (`docs/mcp/connections.md:24`). Локальний `.claude/settings.local.json` (`enabledMcpjsonServers`, у `.gitignore`) вмикає всі три сервери `.mcp.json` у кожній сесії в цій теці, тож розділення сесій тримається на ручному перемиканні. Автоматичний запуск `claude -p` у теці підніме всі сервери з `.mcp.json` без питань |

## Що пишемо в договір

- Які системи клієнта підключаємо і з якими правами: за замовчуванням жодних. Для роботи агента використовуємо окремі копії або одноразові проєкти (Supabase з порожньою схемою й тестовими даними, Vercel з окремим проєктом) і доступ лише на читання, окрім явно названих записуючих дій, кожну з яких схвалює людина вручну.
- **Правило: клієнтський проєкт до агента напряму не підключаємо; працюємо з окремого акаунта без клієнтських організацій.**
- Чиї акаунти: окремий акаунт без клієнтських організацій і команд; його власник і відповідальний за права та відкликання токенів — агенція в особі технічного ліда проєкту. Токен Vercel має увесь акаунт, тому в ньому немає чужих проєктів і способів оплати клієнта.
- Куди їдуть дані клієнта: усе, що агент прочитав (рядки з бази, логи, знімки сторінок, відповіді серверів), потрапляє в контекст моделі, тобто до провайдера LLM (Anthropic, через Claude Code). Через хостед-сервери `mcp.supabase.com` і `mcp.vercel.com` дані йдуть до Supabase і Vercel. Playwright працює локально, але все введене в браузер отримують сайти, які він відкриває. Закомічені транскрипти й докази (`docs/mcp/ab/`, `docs/mcp/evidence/`) потрапляють на GitHub і до сервісу рев'ю PR. Журнали сесій (`~/.claude/projects`) і дампи браузера (`.playwright-mcp/`) лишаються на машині виконавця, тому їх зберігають і чистять за правилами договору.
- Supabase MCP працює з правами розробника й призначений для розробки; клієнтам і кінцевим користувачам його не віддаємо.
- Усе, що змінює дані чи щось публікує (`apply_migration`, `execute_sql`, деплой, зміна статусу), виконується лише з ручним схваленням людини, без «Always allow».
- Зміни `.mcp.json` і `.claude/settings.json` — це зміни прав і проходять рев'ю як код. Автоматичні запуски (`claude -p`, CI) не дозволені в теках із закоміченим `.mcp.json`, поки не налаштовано окремий мінімальний набір серверів.
- Недовірений текст (поля клієнта, логи, коментарі, сторінки) вважаємо даними, а не командами. Інструкції зсередини агент не виконує, а цитує людині.
- Інцидент: підозра на витік або на виконання чужої інструкції означає негайне видалення токенів (`claude mcp remove`), відкликання доступу в акаунтах вендорів і повідомлення клієнта.
